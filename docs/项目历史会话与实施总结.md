## 2. 项目定位与当前架构

仓链管理系统是基于 `RuoYi` / `RuoYi-Vue` 二次开发的前后端分离业务系统，目前定位已经从基础仓储系统逐步扩展为：

> 面向小微商贸、批发、多仓和多门店场景的“仓储 + 进销存 + 财务 + 经营分析”轻量 ERP。

当前主要技术架构如下：

- 后端：Java 8、Spring Boot 2.5.15、Spring Security、MyBatis、Druid、Redis、Quartz、Maven。
- 前端：Vue 3、Vite、Element Plus、Pinia、Vue Router、Axios、Sass。
- 数据库：MySQL 5.7 / 8.0。
- 后端默认端口：`7565`。
- 前端开发代理前缀：`/dev-api`。
- 后端主要模块：`canglian-admin`、`canglian-common`、`canglian-framework`、`canglian-system`、`canglian-quartz`、`canglian-generator`。

后端开发继续遵循现有系统的 `controller -> service -> mapper` 分层方式，SQL 升级脚本保持全小写风格。

## 4. 调研与分析结论

### 4.1 现有代码与架构调研

历史实施前先对以下内容进行了梳理：

- RuoYi 多模块后端结构、权限体系、日志监控、定时任务和代码生成能力。
- 业务 Controller、Service、Mapper、Mapper XML 的真实目录和现有调用方式。
- 客户、供应商、商品、仓库、库位、库存、出入库、调拨、盘点、退货等仓储业务。
- 应收、应付、收款、付款、费用、核销、坏账、发票、成本和报表等财务业务。
- 前端 API、业务页面、菜单路由、权限标识和请求拦截器。
- 初始化 SQL 与不同时间的升级脚本之间的表、字段和菜单 ID 冲突风险。

关键结论是：系统底层框架和基础模块并不缺，主要问题在于业务流程分散、状态联动不完整、数据库版本不统一，以及用户入口和管理视角不足。

### 4.2 金蝶精斗云对标调研

历史会话参考了金蝶精斗云产品页和条码管理资料，得出的主要差距是：

- 原系统以仓储执行单据为主，缺少订单驱动的进销存主线。
- 缺少报价、购销订单、价格优先级、发票登记和最近成交价等商贸能力。
- 缺少扫码开单、扫码盘点、扫码调拨、智能补货和移动协同入口。
- 仓储与应收应付、收付款、核销之间需要更明确的业务财务联动。

因此第一阶段没有重做底层框架，而是在现有仓储和财务底座上补齐轻量 ERP 主链路。

### 4.3 金蝶云星辰对标调研

进一步对标金蝶云星辰后，结论是系统已有进销存基础，但与“业财税一体化经营系统”之间仍有差距，重点缺口包括：

- 凭证完整生命周期和业务单据回写。
- 基础总账接口与期间管理。
- 发票、应收应付和凭证之间的联动。
- 面向经营者的毛利、客户、商品、库存和资金分析。
- 更长期的零售/POS、商城、电商协同、开放 API、移动经营和生产能力。

实施时采用了分阶段策略：先交付商贸标准版/专业版常用闭环，不一次性建设 POS、生产和电商全量能力。

### 4.4 浏览器巡检与运行库调研

浏览器巡检覆盖了登录页、首页、系统管理、基础资料、仓储、采购、销售、库存、财务分析、日志监控和系统工具等入口。

巡检中发现并处理了三类问题：

1. 页面和路由问题：部分菜单存在入口但缺少可加载页面，例如库位、采购订单桥接、统一待办和数据备份入口。
2. 视觉问题：原 RuoYi 默认后台视觉偏旧，深色模式存在白块、低对比文字和图表颜色不适配。
3. 运行库问题：代码和 SQL 已经升级，但部分运行数据库仍缺少 `fin_expense`、金额字段、收付款日期字段或新版业务表。

历史会话曾在一个开发库中实际执行二期补丁并恢复首页报表接口，但这不能代表所有测试库和生产库都已经升级，因此数据库状态仍需按环境确认。

### 8.1 P0：部署前必须完成

#### 8.1.1 逐环境执行并核验数据库升级

代码仓库已有升级脚本，但不能假设所有环境都执行过。每个测试库、预生产库和生产库都应按顺序执行并记录版本：

1. `canglian/sql/upgrade_20260417_schema_alignment.sql`
2. `canglian/sql/upgrade_20260418_jdy_light_erp.sql`
3. `canglian/sql/upgrade_20260422_xingchen_light_erp.sql`
4. `canglian/sql/upgrade_20260512_phase2_delivery.sql`

执行前需要完成数据库备份，执行后需要核对：

- 新表、新字段、索引和菜单权限是否完整。
- 脚本是否可重复执行。
- 老数据是否能正确适配非空字段、默认值和金额字段。
- Redis 中验证码参数等配置缓存是否刷新。

#### 8.1.2 完成真实业务数据的端到端验收

现有验证以编译、构建、页面打开和部分接口为主，还需要使用真实或接近真实的数据完整走通：

`报价/订单 -> 出入库 -> 库存流水 -> 应收应付 -> 收付款 -> 核销 -> 发票 -> 凭证 -> 经营报表`

同时必须覆盖取消、退货、反审核、冲销、重复提交、库存不足、超收超付和并发操作等异常场景。

#### 8.1.3 将数据备份入口升级为真实能力

当前 `dataBackup/index.vue` 明确标注“暂未接入在线备份执行接口”，目前只是人工备份说明页，尚未形成系统内可执行的备份、下载、恢复和审计闭环。

建议后续至少补齐：

- 后端备份任务接口与权限。
- 备份文件保存位置、保留周期和下载控制。
- 备份结果、失败原因和操作日志。
- 恢复演练和可恢复性验证。
- 数据库与上传文件目录的联合备份方案。

#### 8.1.4 生产安全配置复核

- 开发环境可以关闭验证码，生产环境应根据安全要求重新开启。
- 上线前修改默认账号密码，并检查管理员、测试账号和角色权限。
- 数据库、Redis、上传路径、日志路径和跨域配置不得沿用开发默认值。
- 检查配置文件和历史工具目录中是否残留账号、密码或内网地址。

### 8.2 P1：建议下一阶段完成

#### 8.2.1 完整可配置审批流

当前已有审批待办和业务状态，但尚缺少统一、可配置的审批引擎。建议补充销售订单、采购订单、出库、付款、超信用额度等审批规则、审批人配置、驳回和重新提交。

#### 8.2.2 强化移动端和仓库扫码作业

已有扫码开单、盘点和调拨基础能力，后续可继续补：扫码收货、拣货、复核、发货、批次/序列号采集、盘点差异提交和离线容错。

#### 8.2.3 完善批次、序列号和效期闭环

商品档案已具备批次、序列号和保质期字段，但仍应通过业务验收确认入库赋码、库存追踪、先进先出、近效期预警、退货追溯等完整流程。

#### 8.2.4 提升导入能力的可靠性

- 增加大批量导入性能测试。
- 增加导入幂等、重复编码策略和事务回滚验证。
- 输出标准错误文件，包含行号、字段和失败原因。
- 继续补齐期初应收、期初应付和价格体系导入。

#### 8.2.5 加强财务和报表口径验证

- 使用财务人员认可的样例核对金额、税额、成本和毛利口径。
- 验证期间结账/反结账、凭证冲销和发票反向处理。
- 验证多仓、多批次、一对多单据关系下报表不重算、不漏算。
- 增加对账、账龄、信用额度占用和月末检查能力。

#### 8.2.6 建立自动化测试与 CI

历史记录主要证明编译和构建成功，未看到覆盖核心业务的完整自动化测试体系。建议增加：

- Service 单元测试。
- Mapper/SQL 集成测试。
- 核心业务链路接口测试。
- 前端关键页面和路由冒烟测试。
- GitHub Actions 或其他 CI 的编译、构建、测试和 SQL 静态检查。

### 8.3 P2：按产品定位分阶段建设

以下内容在金蝶云星辰对标调研中被识别为长期差距，但不建议在未明确客户场景前一次性全部开发：

- 商城、电商平台订单和库存同步。
- 开放 API、Webhook 和第三方系统集成。
- 生产、委外和 MRP。
- 更完整的移动经营、老板日报和自助报表。
- 多组织、多账套、多币种和更完整税务能力。

## 10. 建议的后续执行顺序

### 第一阶段：形成可验收环境

1. 清点测试、预生产和生产数据库版本。
2. 完成备份后按顺序执行四份升级脚本。
3. 刷新 Redis 配置缓存并重启前后端服务。
4. 对菜单权限、接口和核心页面做一次全量冒烟测试。

### 第二阶段：完成业务闭环验收

1. 准备客户、供应商、商品、仓库、期初库存和期初往来样例数据。
2. 完整跑通采购和销售两条主链路。
3. 验证退货、取消、冲销、反审核和异常库存场景。
4. 由业务、仓库和财务人员共同确认报表口径。

### 第三阶段：补齐上线保障

1. 实现真实备份和恢复能力。
2. 增加自动化测试与 CI。
3. 完善部署文档、角色权限矩阵、业务流程图、接口文档和数据库字典。
4. 清理临时目录并核验 GitLab、GitHub Release 和正式发布记录。

### 第四阶段：按客户需求扩展

根据实际客户场景，再决定是否建设审批引擎、移动仓库、POS、电商同步、开放 API 或生产模块，避免系统在需求未明确前无边界扩张。
